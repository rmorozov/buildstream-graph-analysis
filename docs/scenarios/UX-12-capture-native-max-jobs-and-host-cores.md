# UX-12: capture real native `--max-jobs` + host CPU core count; flag oversubscription

**Priority:** High | **Status:** 🟢 Done | **Depends on:** `UX-09` (the joint-optimization finding this directly closes the cheapest part of)

## Motivation

`UX-09` proved, with real evidence, that `--builders` (BuildStream's own element-dispatch concurrency) and native `--max-jobs` (each element's own internal `make -jN`/`ninja` parallelism) both consume the same physical CPU cores, uncoordinated - and that `bga`'s current capacity model has zero visibility into the second axis. Checking exactly how zero: `tools/bst_extract_run.py:325` sets `resource_capacities.PROCESS = scheduler["builders"]`, and run-context/v9's own `max_jobs` field is - confirmed via `tools/bst_log_to_chrome_trace.py:207-224`'s own docstring - a spec-defined synonym for `builders` itself, **not** the real native `--max-jobs` value ("`--max-jobs` is a different, unrelated concept... and is not what run-context/v9's `max_jobs` field means"). So today, no run-context.json anywhere records the real `--max-jobs` a build was actually invoked with, and none records the host's real CPU core count either. `bga` cannot even show a user "you ran builders=8 × max-jobs=8 = 64 potential concurrent processes on a 4-core host" - the input data for that sentence doesn't exist.

This is the cheap, immediately-actionable half of `UX-09`'s implication - distinct from `UX-11`'s much larger intra-sandbox profiler project, which answers a deeper question ("is a single element's own internal parallelism well-used") that this task does not attempt.

## Required Fix

1. **Capture the real `--max-jobs` value.** It isn't visible in BuildStream's own build log the way `--builders`/`--fetchers`/`--pushers` are (confirmed: those three are parsed from real log lines in `bst_log_to_chrome_trace.py:314-320`; `max-jobs` prints nowhere in the log itself). It has to be captured out-of-band - either as an explicit new CLI flag on `tools/bst_extract_run.py`/`tools/bst_run_wrapped.py` (the caller already knows what they passed to `bst --max-jobs N build`), or by querying `bst show --format '%{max-jobs}'` against the project at extraction time (mirrors how `tools/bst_show_to_graph.py` already queries other per-element fields). Note the second option would need real handling for per-element `max-jobs` overrides (a real, resolvable BuildStream variable, overridable per-element/per-kind) diverging from a single global value - not attempted here; the explicit-flag option (a single global value, matching what the user actually typed) was chosen instead for this task, deferring per-element variance as a known simplification.
2. **Capture host CPU core count** at extraction time (`os.cpu_count()`, or `len(os.sched_getaffinity(0))` where available - the more correct one under cgroup/container CPU limits, which is exactly the kind of real environment `bga`'s own CI runs in).
3. **Store both as new run-context.json provenance fields** - not reusing the already-taken `max_jobs` name (would silently collide with the existing spec-defined field and corrupt `resource_capacities` math). Something like `native_max_jobs` and `host_cpu_count`, clearly separate from `resource_capacities`.
4. **Surface an oversubscription/undersubscription signal.** When `resource_capacities.PROCESS * native_max_jobs > host_cpu_count` by a meaningful margin, emit a soft violation/caveat in `bga analyze`'s output (report text + JSON) naming the real numbers - directly quantifying, per-run, the exact condition `UX-09` demonstrated causes real slowdown (8×8 on 4 cores was ~11% slower than 4×4). Symmetrically, flag meaningful undersubscription (`builders * max_jobs << host_cpu_count`) as a "you may be leaving cores idle" hint - a distinct, real signal from the existing `RESOURCE_WAIT` category (which measures wait for BuildStream's own dispatch slots, not host-core idle time).

## Fix Implemented

1. **`tools/bst_extract_run.py`**: new `--native-max-jobs INT` CLI flag (the caller states what they actually passed to `bst --max-jobs N build` - the explicit-flag option from Required Fix item 1, not the `bst show`-query option). New `_host_cpu_count()` helper: `len(os.sched_getaffinity(0))` where available (correct under a cgroup/container CPU-share limit, e.g. this repo's own CI), falling back to `os.cpu_count()`. Both stored as new, best-effort run-context.json fields (`native_max_jobs`, `host_cpu_count`) - deliberately not reusing the already-taken `max_jobs` name. `native_max_jobs` is also folded into the run-identity manifest's `scheduler` sub-dict (`_compute_run_identity`), matching how `builders`/`fetchers`/`pushers` already gate identity, since it equally affects real observed concurrency/scheduling.
2. **`bga/ingest/models.py`/`bga/ingest/loader.py`**: `RunContext.native_max_jobs`/`.host_cpu_count`, parsed straight from the new JSON fields (both `Optional[int] = None`, absent in the common case where a run-context.json predates this fix).
3. **`bga/analyzer.py`**: new `_check_process_oversubscription` method, called from `analyze()` right after the wall-clock/horizon computation. Only runs when `resource_capacities.PROCESS`, `native_max_jobs`, and `host_cpu_count` are all present (best-effort, matching `UX-10`'s `wall_clock_containment` precedent for a soft, non-hard-gate-affecting violation). Threshold: compares this run's real declared demand (`builders * native_max_jobs`) against what BuildStream's own real defaults would produce on this host (`4 * min(host_cpu_count, 8)` - `builders=4` confirmed in `buildstream/data/userconfig.yaml`, the `min(cores, 8)` cap confirmed in `buildstream/_context.py`'s `effective_build_max_jobs`), rather than an arbitrary constant - this is the exact real-world comparison `UX-09`'s own 4×4-vs-8×8 evidence supports. Emits a `resource_oversubscription` violation when demand exceeds that default, or `resource_undersubscription` when demand falls below one process per core (cores plausibly sitting idle).
4. **`bga/report/text.py`**: explicit human-readable formatting for both new violation types (previously any unrecognized type fell back to a raw dict dump).

This is a coarse, config-level signal - it compares *declared* capacity, not *measured* achieved concurrency, so it can't distinguish (for instance) a high `max-jobs` value that's genuinely oversubscribing cores from one that's simply unused because a given element has too little internal parallel work to fill it (a real distinction `UX-09`'s own evidence surfaced: `examples/05`'s `4×16` config had the same declared demand as `8×8` but wasn't measurably harmful, since each `lib-*.bst` there only has 2 source files). The caveat is honestly a "verify this is helping" signal, not a certain diagnosis of harm - see `UX-14` for the deeper, harder problem of modeling real achieved concurrency.

## Out of Scope

- Any change to `LB`/`efficiency_score` math itself - this task only adds visibility (new fields + a caveat message), not a new bound. See `UX-13` for the report-honesty follow-up and `UX-14` for the deeper replay/sweep modeling gap.
- Remote-execution builds - `UX-09` already established the real bottleneck is invisible to the local client in that mode; this task's oversubscription signal is only meaningful for local sandboxes.
- Per-element `max-jobs` overrides (a real BuildStream possibility - `max-jobs` is a resolvable variable, overridable per-element/per-kind) - this task captures one global value, matching what the user actually passed on the command line; real per-element variance is a known simplification, not attempted here.

## Acceptance Test

1. `tools/bst_extract_run.py` (or a documented wrapper flag) records `native_max_jobs` and `host_cpu_count` in a real run's `run-context.json`.
2. A real re-extraction of `examples/05-cmake-cpp-toolchain`'s `8×8` configuration (the one `UX-09` measured as slower than `4×4`) produces an oversubscription caveat in `bga analyze`'s output naming the real numbers (builders=8, max-jobs=8, host_cpu_count=4).
3. The `4×4` configuration (BuildStream's own real defaults on this host) does not trigger the same caveat.
4. Full suite green.
