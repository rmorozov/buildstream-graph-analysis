## Proposals

Each is marked `optimization`. The architect shapes them; this report
does not.

1. **The browser-share guard compares within one run.** It would gate
   on that run's own junit, not on a reference CI re-adopts after every
   merge. Otherwise its tolerance should be set from a measured
   run-to-run spread, not 1 point. As it stands, a merge reds the next
   unrelated one, and "adopt" is the only fix a pull request can carry.
   Cutting the share is `UX-1354`'s job. This proposal is about the
   guard's shape.
2. **A retro's proposals reach a row, or the next retro says why not.**
   `dev_retro.py` could list the previous `retro-*.md` proposals and
   whether a task file cites each one. Three of three went unfiled
   this week, and the skill ends at the pull request (`UX-999`'s Out of
   Scope), so nothing carries them to the architect.
3. **Re-proposed: a pinned dev dependency is checked against the floor.**
   Last week's proposal 1 stands. `UX-1348` moved the floor; nothing
   reads a pin's `requires_python`. The next pin that outruns 3.12
   reds main's oldest cell unseen again, because pull requests run
   3.12 alone.
