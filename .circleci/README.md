# Manual real-project capture on CircleCI

Connect this GitHub repository as a CircleCI project, then use **Pipelines → Trigger Pipeline**. Select a branch containing `.circleci/config.yml`; add pipeline parameter `run_capture` (boolean) with value `true`. The workflow has no scheduled runs, and ordinary pushes use the default `false`, so they do not start a capture. Set `jobserver` to `auto` to exercise the jobserver; leave it `off` for comparison. Keep `fdsdk_ref`, `target`, `builders`, `max_jobs`, `capture_mode`, `trace_opens`, and `trace_spine` identical between comparison runs. The default target is intended for `incremental` captures; choose a smaller whole closure for `cold`.

The job defaults to a CircleCI Linux VM (`large`, 4 logical vCPUs). `builders=4` and `max_jobs=4` are logical concurrency settings, not a claim of four physical cores. A paid org can pass a different `resource_class` pipeline parameter (such as `xlarge`). The job installs BuildStream and bga, clones the pinned freedesktop-sdk revision, warms and cuts the incremental rebuild set, then captures the build and records its analysis. Download `fdsdk-capture` from the job's Artifacts tab, including partial results if the build fails before CircleCI’s hard runtime limit. Captures stay in CircleCI artifacts; this job never moves the GitHub `captures/fdsdk-latest` branch or writes other capture branches. No GitHub write token is required.

**Free-plan limit:** CircleCI currently caps each Free-plan job at **one hour**. The GitHub workflow documents approximately 65 minutes for a default incremental capture on its runner, so the same run might time out here, especially with tracing or jobserver overhead. The VM might finish it faster, but that must be measured. A cold capture of the default target is known to exceed the job budget. The open-source credit allowance increases available minutes but does not unlock the paid `xlarge` and `2xlarge` VM classes. Check CircleCI's current credit allowance and VM availability before dispatching repeated runs.

The script starts its build with the time remaining in a 50-minute budget measured from job setup, interrupts it at that deadline, and reserves roughly ten minutes for extraction and artifact upload. It skips a plain-build retry after a deadline interrupt. This is a budget, not a guarantee: a slow preflight, slow analysis, or an unresponsive subprocess can still reach CircleCI’s hard one-hour limit, at which point CircleCI does **not** run `store_artifacts`. Check `capture-outcome.txt` and `capture-context.txt` for `deadline_hit=1` before treating a capture as complete. Results from a 4-vCPU CircleCI VM should be compared only against runs with matching capture parameters and runner topology, not merged into a GitHub-hosted baseline without checking those differences.

The `auto` arm reports `nproc` and CPU topology in `capture-context.txt`. The `large` class may expose only two physical cores with SMT; a 4-vCPU off/auto pair does not establish behavior on the 16-core host requested by UX-895. Run `examples/11-serial-giant/calibrate_width.py` on a suitable host before interpreting width scaling. That calibration builds a separate staged toolchain and is not included in this time-limited capture.
